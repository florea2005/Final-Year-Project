\begin{abstract}
	{Students on LZSCC.111 Software Development learn to program in C, where program state is hidden and mistakes often show up only as a wrong number or a crash. This project will build a framework of interactive C exercises that increase in difficulty. In each exercise the student implements a single function. Provided scaffolding handles input and output, and a Python visualiser shows what the code does step by step, such as the bars of an array being searched or a robot moving through a maze. Student code runs inside a C harness that records each step as an event trace and catches crashes, infinite loops and out-of-bounds access. The framework will be evaluated technically and through a small study with students, comparing the exercises with and without the visualiser. The expected outcome is a reusable set of tasks for LZSCC.111, along with indicative evidence on whether visual feedback improves novice understanding and engagement.}
\end{abstract}

\section{Introduction}\label{sec:introduction}

LZSCC.111 introduces students to programming in C. For a beginner, C gives little visible feedback~\cite{smith2000efficacy}. A loop that searches an array or a function that moves a robot produces at most a line of printed output, and the student cannot see how the program reached its result~\cite{fincher2020notional}. Reading input, parsing it and formatting output also take effort unrelated to the concept being taught, so beginners spend their time on scanf and printf instead of the algorithm. Research on algorithm visualisation has found that showing execution helps most when students interact with the visualisation rather than only watch it~\cite{hundhausen2002meta, naps2002exploring}. This project applies that idea to LZSCC.111. Students write only the core logic of each task in C, and a Python visualiser shows its effect.
The rest of this proposal is organised as follows. Section 2 reviews related work and the gap this project addresses. Section 3 sets out the aims and objectives, followed by the methodology. Section 4 describes the programme of work, Section 5 relates to the resources required and last but not least Section 6 reveals the risks and contingencies.

\section{Background and Related Work}\label{sec:background}

Novices learn to program by building a notional machine, a mental model of what happens when code runs~\cite{fincher2020notional}, and an incomplete model causes many misconceptions~\cite{sorva2013notional}. The model is hard to build in C, where state is hidden and errors often appear only as a wrong number or a crash. Smith and Webb showed that visualisation helps novice C programmers~\cite{smith2000efficacy}, although their tool displayed generic memory rather than the concept being taught. Here, each task is visualised in its own terms, such as array bars or a robot in a maze.

Hundhausen et al. found that visualisations work best when students engage with them actively rather than just watching~\cite{hundhausen2002meta}, and Naps et al. formalised this as an engagement taxonomy~\cite{naps2002exploring}. Classic algorithm animations replay pre-built code and so keep students at the “viewing” level. In this framework the animation comes from the student’s own code, which places them at the “constructing” level.

General-purpose tools such as Jeliot 3~\cite{moreno2004} and Online Python Tutor~\cite{guo2013pythontutor} visualise arbitrary programs, and Python Tutor also lets students step backwards. What they display is limited to variables, frames and pointers, not what an algorithm is doing, and most of them support Java or Python rather than C~\cite{sorva2013review}. Microworlds such as Karel the Robot~\cite{pattis1981} make every action visible in a simplified language. The framework combines the two approaches: students write real C, and scaffolding functions emit events that a Python visualiser replays.

Plain-language error messages help novices~\cite{becker2016}, and automated assessment usually compares final output in a sandbox~\cite{ihantola2010review}. Output checks ignore how a student reached the answer, and crashes give little feedback. The C harness therefore reports crashes, timeouts and out-of-bounds errors clearly, keeps the trace up to the point of failure, and compares traces with a reference solution.

Scope. The project will deliver at least one array and one labyrinth task for LZSCC.111, together with the harness, the visualiser, automated tests and a small descriptive user study. It will not deliver a general C visualiser, a grading system or a statistically powered evaluation.

\section{Proposed Project}\label{sec:project}

\subsection{Aims and Objectives}\label{sec:objectives}

The aim of the project is to build a reusable framework of visual C tasks of increasing difficulty,
aligned with the LZSCC.111 curriculum, and to gather evidence on whether it helps students learn. The objectives are:

\begin{enumerate}[label=\textbf{O\arabic*}]
	\item \textbf{} -- Literature review on program visualisation, scaffolding and novice programming. 
	\item \textbf{} -- Design the architecture that connects students' C code to Python visualiser through an event-trace format.
	\item \textbf{} -- Build a C harness that runs code safely, catching crashes, infinite loops and out-of-bounds errors then reporting them in plain language.
    \item \textbf{} -- Implementing (at least 2) tasks with different difficulty, each with C scaffolding, a solution and a visualisation.
    \item \textbf{} -- Automated tests for the framework so that new tasks can be added.
    \item \textbf{} -- Evaluate the framework technically and through a small user study.

    \textit{} The project addresses two research questions:
    
    \textit{} RQ1: How can a visual feedback framework for C be designed so that students implement only the core logic, while new tasks remain easy to add?

    \textit{} RQ2: Do students who use the visual tasks report better understanding and engagement than when they use plain text-based exercises?
    
\end{enumerate}

\subsection{Methodology}\label{sec:methodology}

The project will follow an iterative approach, with a working increment shown to the supervisor every week. This suits the project because each task can be built, tried and adjusted on its own, and early feedback on the first task will shape the design of the rest. A waterfall approach was considered and rejected, since the requirements for later tasks depend on what is learned from the first prototype.

The framework separates student code from visualisation through an event trace. Students solve each task by calling scaffolding functions, such as one that compares two elements or moves the robot, and each function records its action as an event (e.g., “compared index 3”). The C harness writes these events as JSON lines to a separate file, so the student’s printf output does not interfere. The Python visualiser then replays the trace as an animation. Since events are flushed as they occur, a crashing program still leaves a trace up to the point of failure (O3). The trace also lets students step backwards~\cite{guo2013pythontutor} and makes visualisations testable: automated tests compare it against the trace of a reference solution~\cite{ihantola2010review}(O5).

\subsection{Evaluation}\label{sec:evaluation}

The evaluation has two parts, one for each research question. For RQ1, every
task must accept its reference solution and catch a set of deliberately faulty solutions, such as an
off-by-one error, an infinite loop and an out-of-bounds access. The time and lines of code needed
to add a new task will also be measured. For RQ2, participants will solve tasks with and without
the visualiser and then complete a questionnaire on understanding and engagement, including
the System Usability Scale~\cite{brooke1996sus}. Where possible, a short concept quiz will be given before and after the session. Results will be analysed descriptively.

\subsection{Participation and ethics}\label{sec:ethics}

The user study will aim for 10 to 15 participants, current LZSCC.111 students. This size is realistic for the timeframe and enough for a descriptive comparison, though not for statistically significant results.
Participants will receive an information sheet and sign a consent form, and all responses will be anonymised. Ethics approval will be requested early in Michaelmas term so that the study can be done in the Lent term. Participation is voluntary and has no effect on LZSCC.111 marks; participants may withdraw at any time. Data will be stored securely in line with GDPR and deleted after the project.
